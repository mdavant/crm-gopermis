# Annuaire et coordonnées clients

Le tableau Clients utilise une recherche serveur sur **toutes** les fiches et une pagination de 25 résultats. Les totaux proviennent d'un COUNT SQL, sans estimation ou fenêtre de 2 000 clients. Les résultats sont triés par création puis UUID pour stabiliser les pages. Un filtre de statut permet d'affiner la liste ; il ne change pas le statut d'une fiche. La navigation précédente/suivante et le numéro de page suivent les résultats effectivement chargés, avec indicateur de recherche et boutons désactivés pendant la requête.

Migration 004 : fonctions de normalisation, colonne de recherche générée automatiquement, index GIN trigramme, index d'ordre/téléphone/email, version et date de mise à jour. L'extension PostgreSQL pg_trgm doit être disponible pour l'administrateur des migrations, en plus de btree_gist. Le moteur d'aperçu charge les deux extensions. L'index trigramme accélère les recherches par sous-chaîne ; les requêtes très courtes peuvent toujours nécessiter un parcours séquentiel. Aucune promesse de performance à grande échelle sans mesure de charge.

GET `/api/clients/search?q=...&page=1&pageSize=25&status=Actif` renvoie `{items,total,page,pageSize,pages}`. Les paramètres sont validés (page positive, taille de 1 à 100, recherche de 200 caractères maximum). Le total et la page sont lus dans une transaction REPEATABLE READ. GET `/api/clients?q=...` reste compatible : tableau de 100 résultats maximum, recherche SQL complète. Les deux endpoints exigent clients.read.

Le bouton « Modifier les coordonnées » agit sur prénom, nom, téléphone, email et origine, avec clients.write. POST `/api/clients/:id` exige les valeurs et la version lue. Une fiche modifiée entre-temps renvoie 409 et invite à la recharger : pas d'écrasement silencieux. Les mises à jour sans changement n'ajoutent pas un audit artificiel.

Le journal indique auteur/date et noms des champs modifiés, avec versions, sans recopier inutilement toutes les anciennes coordonnées personnelles. Identifiant client, prestations, snapshots tarifaires, paiements, séances et journal d'heures restent conservés. Aucun changement de statut, fusion ou suppression n'est exposé dans ce formulaire.

Les doublons sont contrôlés sur l'email sans distinction de casse et sur le téléphone normalisé ; les formes françaises courantes 06..., +336... et 00336... sont rapprochées. Cela ne prétend pas couvrir tous les plans téléphoniques internationaux. Les créations/modifications API prennent des verrous transactionnels par identité dans un ordre stable : deux écritures concurrentes ne créent pas le même nouveau contact. Aucun index UNIQUE destructif n'est imposé sur des données historiques potentiellement déjà dupliquées. Les doublons existants ne sont ni fusionnés ni supprimés automatiquement. Un administrateur écrivant directement du SQL doit respecter ces règles ou passer par les services métier.

Vérifications exécutées : recherche d'une fiche ancienne hors de l'ancienne fenêtre de 2 000 fiches, pagination sur 2 105 résultats et pages disjointes, filtres/accents/paramètres invalides, correction de coordonnées sans toucher aux prestations ou crédits, refus d'une ancienne version, doublons français, créations concurrentes avec un succès/un conflit, modifications concurrentes avec un succès/un conflit. Le navigateur vérifie l'enregistrement et son retour de réussite, la pagination mobile de 26 fiches sur deux pages et l'absence de débordement horizontal.

La migration 005 ajoute un index de lecture du planning. La vue Planning s'ouvre sur la journée courante à Paris ; le choix d'une autre date est filtré côté SQL avec les limites du jour en Europe/Paris, y compris le changement d'heure. Une séance qui chevauche la journée est incluse. « Toutes les séances » retrouve la liste historique, toujours limitée aux 500 dernières entrées. La fiche client conserve toutes ses séances dans cette même limite. Ce n'est pas encore une grille calendrier hebdomadaire ou une politique d'annulation.
